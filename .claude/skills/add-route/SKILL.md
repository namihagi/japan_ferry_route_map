# 航路を追加・照合する

用語は [`CONTEXT.md`](../../../CONTEXT.md)、台帳の書き方は [`data/README.md`](../../../data/README.md) に従う。1回の作業では、運航会社単位でまとめて進める。

## 1. 対象航路か判定する

CONTEXT.md の「対象航路」に当てはまるものだけを追加する。

- 貨物フェリー（一般の旅客が乗れない）、周遊型の遊覧船、国際航路、廃止済みの航路は入れない。
- 同じ会社でも船種が違えば別の航路にする（例：フェリーと高速船）。

**完了の条件**：追加する航路ごとに、運航会社・船種・寄港地の並びが決まっている。

## 2. 公式サイトで照合する

運航会社の公式サイトで、次の5項目を確かめる。

1. 航路名
2. 運航会社
3. 寄港地
4. 船種（車両を積めるか。高速船か）
5. 運航状態（運航中／休止中）

補足：

- 「休航」「運休」が一時的な欠航（天候・ドック入り）なら運航中のまま。航路そのものの休止なら `suspended` にし、`note` に根拠を書く。
- 所要時間は、公式サイトに書いてあるときだけ `durationMinutes` に入れる。
- 公式サイトに載っていない航路は、廃止の可能性があるので追加しない。
- 取得のコツ：ページ全体を読むより、`curl` で取得して上の項目のキーワード周辺だけを抜き出すほうが速い。

**完了の条件**：5項目すべてについて、根拠となる公式ページの URL を `verification.sources` に書ける。

## 3. 実測形状（OSM の way）を探す

OSM の `route=ferry` の way を探す。Overpass API は混雑で失敗しやすいので、失敗したら時間を置くか、別のエンドポイント（`overpass.kumi.systems`、`overpass.private.coffee`）で試す。

```
[out:json][timeout:120];area["ISO3166-1"="JP"][admin_level=2]->.jp;
way["route"="ferry"]["name"~"<運航会社名や港名>"](area.jp);out tags geom;
```

- way の端が港から 3 km 以内にあること。
- 1本の way が複数の区間にまたがってもよい（寄港地で自動的に切り分ける）。
- 見つからない区間は `osmWays` を書かない。その区間は推定形状になる。

**完了の条件**：各区間について、使う way ID を決めたか、推定形状にすると決めた。

## 4. 台帳を書く

- **港**：`data/ports.yaml` に既存の港があれば、それを使う。同じ名前で呼ばれる港は、ターミナルが 1〜2 km 離れていても1つにする。新しい港の座標は、OSM のフェリーターミナルか way の端点から取る。
- **航路**：`data/routes/<id>.yaml` を書く。`id` は `<会社>-<港>-<港>` のように英小文字とハイフンで付ける。

## 5. データを作って確かめる

```sh
pnpm data:import-osm   # OSM API から way を取り込む
pnpm data:estimate     # 推定形状の区間があれば（data/README.md「推定形状」）
pnpm data:build        # 台帳の誤りや、港と線のずれがあればここで失敗する
```

推定形状を新しく計算した区間は、陸を横切っていないか、不自然に遠回りしていないかを目で確かめる。

**完了の条件**：`pnpm data:build` が通り、新しい推定形状をすべて目で確かめた。

## 6. PR にする

- まとまった数（10〜30航路程度）ごとにブランチを切って PR にする。
- PR の本文には、照合した航路の一覧（航路・運航会社・運航状態・形状の出どころ）と、照合で判断に迷った点を書く。
